The Unfettered Terminal Incident

APEXCORP PRODUCTION INCIDENT REPORT

At 02:14 UTC, an SRE switched Claude Code into bypassPermissions mode to "speed up" a routine API route refactoring task across microservices.

The agent misinterpreted a cleanup prompt, executing an unconstrained rm -rf on shared volume configs and pushing an untested commit directly to production, bypassing staging gates.

ERROR: Critical shared volume state destroyed. Lack of permission boundaries and human verification gates.

"deny": [] // Zero deterministic boundaries configured! } // Terminal Execution Trace: $ claude "refactor legacy /v1 routes and clean unused config files" [Agent Loop] Exploring codebase... // ROOT CAUSE ANALYSIS

The Cost of Speed Over Oversight

Unconstrained Autonomy

In bypassPermissions, Claude Code suppresses all interactive confirmation dialogs for file writes and shell commands, trusting prompt interpretations blindly.

Missing Deny Rules

Neither the user settings nor the project settings specified non-overridable deny patterns to guard against dangerous shell commands (rm, git push --force).

No Human-in-the-Loop Gate

High-blast-radius actions (destructive shell commands, writing outside working dir) must be deterministically gated by human approval.

// ARCHITECTURE

The Explore • Plan • Code Loop

Three-Phase Loop Mechanics

1. Explore Phase: Reads files, traces logic, gathers repo context. Read-only tools invoked without state modification.
2. Plan Phase: Synthesizes findings, proposes specific file diffs and tool executions in a structured plan.
3. Code Phase: Executes file edits, runs tests, and applies terminal commands once released by the permission gate.
// How Permission Modes Plug into the Loop: [User Task Given] │ ▼ ┌──────────────┐ │ EXPLORE LOOP │ ──> Reads files (Auto in most modes) └──────┬───────┘ ▼ ┌──────────────┐ │ PLAN PHASE │ ──> Proposes changes └──────┬───────┘ ▼ [PERMISSION GATE] ──> "plan" mode STOPS here! │ "default" asks user confirmation ▼ ┌──────────────┐ │ CODE PHASE │ ──> Writes files, runs commands └──────────────┘
// PERMISSION TAXONOMY

The Four Permission Modes

Mode Auto-Approves Interactive Prompt Required Best Suited For
default Read-only exploration All file edits, shell commands, MCP calls Unfamiliar codebases, high-stakes tasks
acceptEdits File reads & edits inside working dir Shell commands & writes outside repo Rapid feature development & refactoring
plan Read-only exploration & plan generation BLOCKED: No file edits or commands allowed Architectural review, read-only code audits
bypassPermissions Everything (Edits, Shell, MCP) NONE (Except non-overridable Deny rules) Sandboxed CI/CD ephemeral containers ONLY
// CONFIGURATION SCOPES

Settings Hierarchy Precedence

1. Enterprise Level (managed-settings.json)

Admin deployed. CANNOT be overridden by developers or repos. Used for mandatory deny rules and OAuth.

2. Project Level (.claude/settings.json)

Committed to repo root. Shared across all team members who clone the repository.

3. User Level (~/.claude/settings.json)

Developer's personal global configuration across all local projects.

// Enterprise Enforced Settings: managed-settings.json { "defaultMode": "default", "deny": [ "rm -rf *", "git push --force*", "*.env", "/etc/*" ], "allowModeOverride": false // Prevents CLI flags like --dangerously-skip-permissions }
// DETERMINISTIC DEFENSE

Deterministic Deny Rules

Why Instructions in CLAUDE.md Fail

Instructions like "Never run rm -rf" in CLAUDE.md are probabilistic. As context windows grow, prompt instructions can be forgotten or deprioritized.

Deny Rules are Deterministic

The deny array is enforced at the harness layer by Claude Code before the tool call or terminal command is dispatched. Even in bypassPermissions, a denied rule halts execution immediately.

// .claude/settings.json — Project Level Guardrails { "deny": [ "rm -rf", "git reset --hard", "sudo *", ".env*", "**/*.pem" ] } // What happens on violation: $ claude "delete stale keys: rm -rf keys/" [BLOCKED] Action denied by project security configuration. Matched deny rule: 'rm -rf'
// HUMAN-IN-THE-LOOP (HITL)

Calibrated Trust & Gate Placement

Auto-Approve (Low Risk)

• Grep / codebase exploration
• Unit test execution in sandboxes
• Scoped documentation edits
• Formatting & lint fixes

Prompt Gate (Medium Risk)

• Modifying core business logic
• Installing new npm/pip packages
• Editing CI/CD workflows
• Database schema migrations

Deterministic Block (High Risk)

• Destructive filesystem operations
• Direct production deployments
• Reading or modifying private keys
• Force-pushing version control

Practice Question: Settings Precedence

Scenario: An enterprise administrator sets a rule denying edits to *.env in managed-settings.json. A developer working on a high-speed bug fix adds "defaultMode": "bypassPermissions" to their local .claude/settings.json. What happens when Claude Code attempts to modify .env.production?

A. Claude Code modifies .env.production because project-level settings override enterprise managed settings.
B. Claude Code pauses and prompts the developer for interactive confirmation before writing to the file.
C. The action is blocked deterministically because enterprise managed-settings.json cannot be overridden by user or project files.
D. Claude Code creates an isolated subagent to perform the write outside the main conversation context.
Correct! Option C: Enterprise level configuration (managed-settings.json) has highest precedence and cannot be overridden by project-level (.claude/settings.json) or user-level (~/.claude/settings.json) configurations, even in bypassPermissions mode.
// CERTIFICATION CHEAT SHEET

Lesson 1 Master Rules for CCDV-F

1. Plan Mode Stops at Plan

plan mode runs the Explore phase and constructs the plan, but strictly prevents writes and shell executions. Ideal for safe exploration.

2. Hierarchy Precedence

managed-settings.json (Enterprise) > .claude/settings.json (Project) > ~/.claude/settings.json (User).

3. Deny Rules are Inviolable

Deny rules in settings files block actions deterministically before execution, regardless of mode.

4. Human Gate Placement

Place human review gates whenever action cost/reversibility is asymmetric (destructive commands, secrets, production deploys).
