// ROOT CAUSE ANALYSIS
Incident #403-MCP: Three Cascading Failures
Failure 1: bypassPermissions on Live Codebase
// .claude/settings.json — ApexCorp APEX-AI Engine v3 { "defaultMode": "bypassPermissions", "allowedTools": ["*"] // No deny rules. No path restrictions. No guardrails. }

bypassPermissions removed ALL confirmation prompts, including for file deletions. When the MCP pattern-match ran broader than intended, production config files were deleted without a single safety checkpoint. With no deny rules defined, there was nothing to stop it — the mode that was meant to "speed up development" became a demolition tool.

Failure 2: Inline API Key in .mcp.json
// .mcp.json — COMMITTED TO REPO (PUBLIC BRANCH) { "headers": { "Authorization": "Bearer sk-prod-abc123..." } } // Key exposed in git history even after file is overwritten

The production API key was hardcoded directly into .mcp.json, which was committed to the shared repository. Even after the team deleted the key from the file, it persisted in git history. The key had to be treated as permanently compromised, requiring full rotation — breaking every downstream consumer simultaneously.

Failure 3: 847-Line CLAUDE.md Rule Dilution
// Session log — CLAUDE.md rule ignored during incident // Line 1-346: coding style, linting config, PR templates... Line 347: "Never modify files in /infra/prod/ without approval" // Line 348-847: more style rules, API conventions, naming... // Result: Critical path restriction buried, weight diluted → ignored

Critical restrictions buried deep inside a massive CLAUDE.md are probabilistic at best. The model's attention to any specific instruction decreases as file size grows. Path restrictions at line 347 of an 847-line document were effectively invisible — only hooks provide deterministic enforcement.

EXAM REALITY: All three failure modes are tested on CCDV-F. Know how to prevent each one.
// FOUNDATION CONCEPT
Permission Modes: Risk Architecture, Not Speed Settings
// .claude/settings.json — Permission Mode Configuration // MODE 1: default (safest) { "defaultMode": "default", "deny": ["Bash(rm -rf *)", "Write(/infra/prod/**)"] } // MODE 2: acceptEdits (moderate) { "defaultMode": "acceptEdits", "deny": ["Write(.env*)", "Write(/secrets/**)"] } // MODE 3: plan (read-only planning) { "defaultMode": "plan" // Reads and plans only — no writes executed } // MODE 4: bypassPermissions (DANGEROUS) { "defaultMode": "bypassPermissions", // MUST have deny rules or this is a loaded gun "deny": [ "Write(/infra/**)", "Write(.env*)", "Bash(rm *)" ] } // Enterprise scope deny — cannot be overridden: // managed-settings.json (admin-controlled) { "deny": ["Bash(curl * | bash)"] }
default
Prompts for every tool use. Maximum visibility. Use for unfamiliar codebases or any production-touching work. Slowest but safest.
acceptEdits
Auto-approves file edits; still prompts for shell commands. Good for iterative development. Pair with deny rules on sensitive paths.
plan
Read and plan only — no writes are executed. Use for audits, code reviews, and architecture analysis without risk of accidental changes.
bypassPermissions
Removes ALL confirmation prompts — including unexpected ones. Only safe in isolated sandboxes with explicit deny rules covering every critical path. Never use on live codebases without deny rules.
Key Exam Insight: Deny rules always win over allow rules — at any scope. Enterprise-level deny rules in managed-settings.json cannot be overridden by individual developers, even when using bypassPermissions mode.
// IMPLEMENTATION PATTERN
CLAUDE.md, Rules Files & Hook Enforcement
## CLAUDE.md — Project context (probabilistic) ## Place at repo root or ~/.claude/CLAUDE.md # ApexCorp AI Engine — Project Rules ## Critical Path Rules (keep SHORT & first) - Never write to /infra/prod/ without explicit approval - Never commit credentials inline — use env vars only - Always run lint before committing ## Tech Stack Node.js 20, TypeScript, PostgreSQL, Redis --- ## Rules file — YAML frontmatter (scoped) ## .claude/rules/security.md --- name: security-baseline description: Security rules for all sessions alwaysApply: true --- Never echo secrets to stdout. Prefer environment variable references. --- ## PreToolUse hook — deterministic enforcement ## .claude/hooks/block-prod-writes.sh #!/bin/bash INPUT=$(cat) TOOL=$(echo "$INPUT" | jq -r '.tool_name') PATH_ARG=$(echo "$INPUT" | jq -r '.tool_input.path // ""') if [[ "$TOOL" == "Write" && "$PATH_ARG" == "/infra/prod/"* ]]; then echo '{"decision":"block","reason":"prod write blocked"}' exit 0 fi echo '{"decision":"approve"}'
CLAUDE.md
Project memory injected into every session. Probabilistic — dilutes with size. Keep critical rules at the top, under 200 lines total. Supports project, user, and global scopes.
Rules Files
Markdown files with YAML frontmatter. Can be scoped (always apply, path-matched, or on-demand). Loaded from .claude/rules/. Cleaner organization than monolithic CLAUDE.md.
Hooks
DETERMINISTIC — fires at every lifecycle event regardless of mode. PreToolUse can block; PostToolUse can audit. Shell scripts that receive tool call JSON via stdin and return a decision.
Subagents
Specialized Claude instances spawned for delegated tasks. Can have their own CLAUDE.md, permission mode, and tool scope. Isolate risky operations from the main agent context.
Critical Exam Distinction: CLAUDE.md instructions are probabilistic — they can be ignored or diluted. PreToolUse hooks are deterministic — they fire every single time, regardless of context, model decisions, or permission mode.
// COST & LATENCY OPTIMIZATION
Prompt Caching & RAG: Defeating the Context-Cost Problem
// Prompt Caching — cache_control field placement { "messages": [ { "role": "user", "content": [ { "type": "text", "text": "<large system context...>", "cache_control": { "type": "ephemeral" // Breakpoint: cache everything above this point } }, { "type": "text", "text": "<more stable context...>", "cache_control": { "type": "ephemeral" } // Max 4 breakpoints per request } ] } ] } // MCP Tool Discovery — server exposes tools dynamically // Claude lists available tools from MCP server: tools/list → returns tool definitions with schemas tools/call → executes a specific tool by name // Agentic RAG — model decides when to search search_codebase(query="auth middleware") → retrieves chunks // vs classical RAG: always pre-retrieves fixed chunks
Prompt Caching — TTL Rules
5-minute TTL — ephemeral cache for session context.
1-hour TTL — extended cache for stable content (Claude.ai).
Minimum 1024 tokens required to trigger caching.
Cache reads cost ~10% of full token price. Write is 25% more. Saves 90% on repeated large context.
Cache Breakpoint Strategy
Place breakpoints after stable content (system prompts, project docs). Content before each breakpoint is cached. Maximum 4 breakpoints per request. Stack breakpoints from largest to smallest stable chunk.
Classical RAG vs Agentic RAG
Classical RAG: Always retrieves fixed chunks at query time — static, predictable, cheaper.
Agentic RAG: Model decides when and what to retrieve using MCP tools — dynamic, context-aware, more accurate for complex queries.
MCP Tool Discovery
MCP servers expose dynamic tool catalogs. Claude calls tools/list to discover available operations, then tools/call to execute. This allows servers to add or modify tools without client code changes.

Enterprise Authentication: OAuth, Secrets, and the Audit Trail
❌ BEFORE — Credential Exposure
// .mcp.json — NEVER DO THIS { "headers": { "Authorization": "Bearer sk-prod-9x2kLm...", "X-API-Secret": "apex_secret_8f3k..." } } // Even after overwrite — git history retains key forever // git log --all -p .mcp.json | grep Authorization
✓ AFTER — Environment Variable Reference
// .mcp.json — SAFE pattern { "headers": { "Authorization": "Bearer ${WAREHOUSE_MCP_TOKEN}" }, "env": { "WAREHOUSE_MCP_TOKEN": "${WAREHOUSE_MCP_TOKEN}" } } // Token lives in .env (gitignored) or secret manager // Rotate without touching codebase
// PostToolUse Audit Hook — logging every write #!/bin/bash INPUT=$(cat) TOOL=$(echo "$INPUT" | jq -r '.tool_name') TIMESTAMP=$(date -u +"%Y-%m-%dT%H:%M:%SZ") echo "$TIMESTAMP $TOOL" >> ~/.claude/audit.log
OAuth Pattern
MCP over HTTP supports OAuth 2.0. The MCP server acts as resource server; Claude's client obtains a token from the authorization server. Token is passed in the Authorization header. No static secrets in config.
Service Identity Pattern
In production, inject tokens at runtime via secrets manager (AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager). MCP server receives token from environment, never from committed config file.
PostToolUse Audit Hook
Fires after every tool execution. Use to log all Write, Bash, and MCP tool calls with timestamps to an immutable audit log. Essential for SOC 2 / ISO 27001 compliance and incident post-mortems.
Enterprise Managed Settings Lock
managed-settings.json is admin-controlled. Deny rules here are non-negotiable — no developer or permission mode can override them. Use to enforce org-wide security baseline.

            Practice Question — Permission Modes & Hook Lifecycle
          


          

            QUESTION
            A Claude Code project uses acceptEdits mode. A PreToolUse hook is configured to block writes to .env.production. During a session, the developer switches to bypassPermissions. Which of the following statements is TRUE?
          


          

            A
            The hook still fires and blocks writes to .env.production because hooks are lifecycle-bound, not mode-bound.
          

          

            B
            The hook is disabled because bypassPermissions overrides all configuration layers.
          

          

            C
            The .env.production file is protected because acceptEdits mode's protected-path guard remains active.
          

          

            D
            The developer must add a separate allow rule to maintain hook functionality in bypass mode.
          


          

            ✓ CORRECT — Option A
            Hooks fire at their lifecycle event regardless of the permission mode in effect. bypassPermissions removes user confirmation prompts but does not disable hooks. This is precisely why hooks are the preferred enforcement mechanism for critical path restrictions — they are deterministic across all modes, including bypass mode. The PreToolUse hook will still receive the tool call, evaluate the path, and return a block decision.

            Module 3 Master Rules: What CCDV-F Tests
          


          

            
            

              
PERMISSION & ENFORCEMENT


              

                

                  
                  1. Deny Rules Override Everything
                

                
A deny rule at enterprise scope wins over any allow rule and cannot be overridden by individual developers, even in bypassPermissions mode. Configure deny rules before enabling any elevated mode.

              


              

                

                  
                  2. Hooks Are Deterministic; Instructions Are Probabilistic
                

                
A CLAUDE.md rule can be diluted, ignored, or misinterpreted — especially in long files. A PreToolUse hook fires every single time regardless of context, model decisions, or permission mode. Use hooks for all critical path enforcement.

              


              

                

                  
                  5. Scope Hierarchy
                

                
Enterprise (managed) > Project (.mcp.json) > User (~/.claude.json) > Local. Higher scope wins on conflicts. Deny rules at any higher scope block lower scope allows.

              

            


            
            

              
TRANSPORT, SCOPE & SECRETS


              

                

                  
                  3. stdio = Local Only; HTTP = Remote/Shared
                

                
Transport and scope are independent but their combination must match intent. A stdio server in .mcp.json looks shareable in the config file — but it is not. It runs a local process. Only HTTP transport enables true team-sharing and remote access.

              


              

                

                  
                  4. Credentials in Config = Permanent Exposure
                

                
An inline key committed to .mcp.json enters git history forever. Overwriting the file or deleting the key does not remove it from git history. Any key committed even once must be treated as compromised and rotated immediately. Always use environment variable references.

              


              

                

                  
                  6. CLAUDE.md Size = Attention Dilution
                

                
Every instruction added to CLAUDE.md reduces the effective weight of every other instruction. Keep files concise. Place critical rules at the top. For non-negotiable enforcement, always use hooks — not documentation.
