// STREAM PROTOCOL SPECIFICATION

The SSE Event Order in Messages API

1. message_start

Initial message object: id, role ("assistant"), model name, empty content.

2. content_block_start

Starts a block at index. Can be type: "text", "tool_use", or "thinking".

3. content_block_delta

Incremental payload: text_delta, thinking_delta, or input_json_delta.

4. content_block_stop

Signals end of block at index.

5. message_delta & message_stop

Final stop_reason ("end_turn", "tool_use", "max_tokens") + token usage metrics.

# Raw SSE wire representation
event: message_start
data: {"type": "message_start", "message": {"id": "msg_01", "role": "assistant"}}

event: content_block_start
data: {"type": "content_block_start", "index": 0, "content_block": {"type": "text", "text": ""}}

event: content_block_delta
data: {"type": "content_block_delta", "index": 0, "delta": {"type": "text_delta", "text": "Hello"}}

event: content_block_stop
data: {"type": "content_block_stop", "index": 0}

event: message_delta
data: {"type": "message_delta", "delta": {"stop_reason": "end_turn"}}

event: message_stop
data: {"type": "message_stop"}
// TOOL STREAMING

Assembling Streaming Tool Calls

When Claude streams a tool invocation, tool parameters arrive in fragmented JSON chunks via input_json_delta.

Crucial Developer Trap:

You CANNOT call json.loads() on individual deltas! You must buffer the string accumulator until content_block_stop arrives.

Using the Python SDK helper:

Use stream.get_final_message() which automatically accumulates and parses all block types for you safely.

# Manual accumulation pattern for tool arguments
current_tool = {}
json_buffer = ""

for event in stream:
  if event.type == "content_block_start":
    if event.content_block.type == "tool_use":
      current_tool = {"id": event.content_block.id, "name": event.content_block.name}
      json_buffer = ""
  elif event.type == "content_block_delta":
    if event.delta.type == "input_json_delta":
      json_buffer += event.delta.partial_json
  elif event.type == "content_block_stop":
    # Only parse AFTER stop event!
    current_tool["input"] = json.loads(json_buffer)
// RESILIENCE & FAULT TOLERANCE

Recovering from Disrupted Streams

In mobile or high-traffic production environments, sockets close or TCP connections reset mid-stream.

The Truncated Tool Risk:

If a stream dies mid-tool-call, executing the partial JSON causes unhandled exceptions. Never execute a tool unless content_block_stop was received!

Clean Recovery Strategy:

Discard the partial unfinalized assistant block and retry the turn. Use prompt caching so re-sending prior turns is instant and cheap.

# Production Stream Guardrail
try:
  message_completed = False
  with client.messages.stream(...) as stream:
    for event in stream:
      handle_event(event)
      if event.type == "message_stop":
        message_completed = True
  if not message_completed:
    raise StreamInterruptedError("Socket dropped")
except (StreamInterruptedError, APIConnectionError):
  logger.warning("Stream dropped. Discarding partial turn & retrying.")
  retry_call_with_backoff(messages)

// ANTI-PATTERNS

The Stream Assembly Anti-Pattern

Committing Before message_stop

Appending the assistant turn to message history on content_block_stop instead of waiting for message_stop.

# DANGEROUS: If network dies before stop_reason,
# you have committed a broken state to database!
Two-Phase Commit

Accumulate in memory first. Only persist the assistant turn into your database or agent state machine once the stream closes cleanly.

# SAFE: Only write to persistent store
# after message_stop is acknowledged!

In an agentic pipeline consuming an SSE stream from the Claude Messages API, where is the final stop_reason ("end_turn" or "tool_use") delivered?
A. In the message_start event payload at the very beginning.
B. Inside every content_block_delta chunk.
C. In the message_delta event right before message_stop.
D. In the HTTP response headers.
Correct! Option C: The message_delta event is sent near the end of the stream, containing the final stop_reason and cumulative token usage statistics.
// CERTIFICATION CHEAT SHEET

Streaming Takeaways for CCDV-F Exam

1. Buffer Tool Chunks

Accumulate input_json_delta until content_block_stop before calling json.loads().

2. Disconnect Recovery

Never execute unfinalized partial tool calls if socket terminates prematurely.

3. Two-Phase Commit

Only write to persistent session memory once message_stop is confirmed.

4. SDK Convenience

Prefer stream.get_final_message() to handle edge cases automatically.
