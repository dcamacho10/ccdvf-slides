The Three Pillars of a Production Tool

# Production tool definition structure
{
  "name": "lookup_order",
  "description": "Fetch order status, items, and tracking info. Use this when the customer provides an order ID like ORD-12345.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "pattern": "^ORD-[0-9]{5}$",
        "description": "The 8-character uppercase identifier."
      }
    },
    "required": ["order_id"]
  }
}
1. Tool Name Must match regex ^[a-zA-Z0-9_-]{1,64}$. Keep it concise, domain-specific, and snake_cased.
2. Description (Crucial!) Claude reads this like an API directory. It must state what it does, when to invoke it, and what edge cases exist. Vague descriptions lead to under-calling!
3. input_schema (JSON Schema) Root MUST be "type": "object". Always define "required" array so mandatory fields aren't skipped.
// API LEVEL ENFORCEMENT

Strict Tool Use: Zero Hallucinated Types

In standard tool use, Claude generates arguments as unconstrained tokens. While Claude adheres closely, unexpected inputs can produce subtle schema slips.

strict: true

Enables constrained decoding at the token level. The API physically prevents generation of any token that violates your JSON schema.

Tradeoffs to Remember:
  • First request incurs small compilation latency (cached 24 hrs).
  • Injected schema prompts consume input tokens.
  • Must handle stop_reason: "max_tokens" (truncation breaks syntax).
# Enabling strict tool use in Python SDK
tools = [
  {
    "name": "transfer_funds",
    "description": "Initiates an irreversible bank transfer.",
    "strict": True,
    "input_schema": {
      "type": "object",
      "properties": {
        "account_id": {"type": "string"},
        "amount_cents": {"type": "integer", "minimum": 1}
      },
      "required": ["account_id", "amount_cents"],
      "additionalProperties": False
    }
  }
]
// PARALLEL CONCURRENCY

Parallel Tool Calls: Single Assistant Turn

When a user asks: "Check weather in Tokyo and Paris", Claude 3.5 Sonnet returns two tool_use content blocks in the same assistant turn.

⚠️ The Golden Exam Rule:

You MUST return all tool results in a SINGLE user turn. Appending multiple user messages consecutively triggers an immediate API validation error!

Async Execution Pattern:

Dispatch the parallel calls concurrently with asyncio.gather() or thread pools to minimize end-to-end latency!

# 1. Assistant response contains 2 tool_use blocks:
response.content = [
  ToolUseBlock(id="toolu_01A", name="get_weather", input={"city": "Tokyo"}),
  ToolUseBlock(id="toolu_02B", name="get_weather", input={"city": "Paris"})
]

# 2. CORRECT: One user turn with all tool_result blocks:
messages.append({
  "role": "user",
  "content": [
    {"type": "tool_result", "tool_use_id": "toolu_01A", "content": "22°C Clear"},
    {"type": "tool_result", "tool_use_id": "toolu_02B", "content": "18°C Rain"}
  ]
})
// RESILIENCE & ERROR RECOVERY

Error Handling: The is_error Flag

# Handling exceptions gracefully in tool execution
try:
  output = run_database_query(block.input)
  result_block = {
    "type": "tool_result",
    "tool_use_id": block.id,
    "content": json.dumps(output)
  }
except DatabaseTimeoutError as err:
  # Inform Claude of the error so it can adapt
  result_block = {
    "type": "tool_result",
    "tool_use_id": block.id,
    "is_error": True,
    "content": f"Query failed: {str(err)}. Try refining filters."
  }
Why not crash the script?

Crashing crashes the user session. By returning is_error: True, Claude understands the tool execution failed, reads the error message, and can either try an alternate tool or apologize politely.

What stop_reason to watch for?

When Claude intends to invoke a tool, response.stop_reason is "tool_use". When it has finished its final message, it is "end_turn".

Calibrating the tool_choice Parameter

tool_choice: {"type": "auto"}

Default Behavior

Claude decides whether to answer directly with text or invoke one or more tools based on context.

tool_choice={"type": "auto"}
tool_choice: {"type": "any"}

Forced Tool Call

Forces Claude to call at least one tool from the provided list, rather than responding with text. Claude picks which tool.

tool_choice={"type": "any"}
tool_choice: {"type": "tool", "name": ...}

Forced Specific Tool

Forces Claude to call that exact named tool. Ideal for structured extraction workflows where you want guaranteed invocation.

tool_choice={
  "type": "tool",
  "name": "record_event"
}

The Three Classic Schema Traps

1. The Vague Description
"description": "Executes query."

Claude cannot differentiate between multiple tools or know what arguments to supply. Always specify intent and examples.

2. Missing "required" Array
// "required" omitted

JSON Schema standard treats all fields as optional unless explicitly listed in "required": [...]. Claude may drop required fields!

3. Schema Drift in Loops
strict: False

In deep multi-turn loops, unconstrained parameters may morph types (e.g. integer becoming string "42"). Use strict: true.

Practice Exam Question

A developer configures an agent that executes tools. During testing, Claude calls a database tool, but the database connection times out. How should the developer handle this failure to maintain agent continuity?
A. Raise a Python exception to crash the process so Kubernetes restarts the container.
B. Append a user message with a tool_result block having "is_error": True and a descriptive error message.
C. Re-prompt Claude from scratch with temperature set to 0.0 without the tool definition.
D. Return an HTTP 400 Bad Request to the Anthropic Messages API.
Correct! Option B: Returning is_error: True inside the tool_result content block allows Claude to observe the failure reason, self-correct, explain the issue to the user, or try a fallback tool.
// CERTIFICATION CHEAT SHEET

Tool-Use Key Rules for CCDV-F Exam

1. Tool Result Turn Structure

Single user message containing all parallel tool_result blocks matching each tool_use_id.

2. Strict Mode Guarantee

strict: true enforces token-level JSON Schema adherence via constrained decoding.

3. stop_reason Signals

"tool_use" = Claude expects tool execution & results.
"end_turn" = Claude finished its conversational task.

4. Error Reporting

Use is_error: true in tool_result to let the agent adapt instead of crashing.
